# M3 plan

M3 scope and its exit sentence are in [MVP.md](MVP.md). This file puts that scope in order. What has actually landed goes in `STATUS.md`.

**M3 is done when:** scripted concurrent-edit scenarios from the M0 fixtures all end in either a clean merge or a resolvable conflict view, with no lost bytes; a three-version site builds and serves with correct cross-version URLs; renaming a page in the editor yields one PR containing the move, the redirect and updated links, and the old URL redirects after merge.

## Where M2 leaves things

- **Conflicts.** `rebaseDrafts` (`packages/drafts/src/rebase.ts`) merges a drafted file with `git merge-file` when the base moves. A clean merge updates the draft; any conflict marks the whole draft `conflicted` and leaves its files untouched, with the old `base_sha`. Nothing resolves a conflict yet: the user can only discard. The PR-branch half of H2 (`--force-with-lease=<ref>:<sha>` on every push, a merge commit when someone else pushed) is done in `proposeDraft`.
- **Versions.** `oxybook.yml` `versions:` is parsed (`packages/renderer/src/config.ts`), and `buildSiteVersion` already takes a URL prefix and version links. But sync and reconciliation follow only the default ref, and `runSpaceBuild` builds one version, called `default`.
- **Renames.** Drafts and `commitFiles` support a `rename` op. Sync records out-of-band renames in `inferred_redirects`, and the build serves them. `redirects:` in `oxybook.yml` is parsed and served. Nothing renames from the editor, rewrites inbound links, or writes `redirects:`.
- **Ordering.** The theme orders the sidebar from `_dir.yml`. Nothing edits `_dir.yml`.
- **Open-draft indicator.** Done in M2 (`othersEditing` in the tree and on the page).

## Order, and why

Conflicts first: H2 is the riskiest open problem, and M2 leaves conflicted drafts with no way forward but discard. Renames next, because they reuse the draft and PR machinery and need two byte-exact writers (`oxybook.yml` redirects, link destinations) that `_dir.yml` ordering reuses later. Versions after that: they touch sync, reconciliation, the build and the editor, but carry no byte-preservation risk. Then ordering, then the exit script.

Every writer in M3 follows the M0 rule: change only the bytes asked for. YAML edits go through the `yaml` `Document` API, the way frontmatter edits already do. Link rewrites patch the destination span and nothing else.

## Out of scope for M3

- Real-time co-editing and locking (non-goal for v1, ARCHITECTURE §4.5).
- Custom domains, private sites, email, and SSO (M4 and later).
- Editing table structure and raw blocks visually (source mode covers both).
